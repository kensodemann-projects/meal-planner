## Findings

[CLN-001]
**Issue:** In `src/components/sources/SourceEditor.vue`, `save()` trims `description` and `url` before building the payload, but `isModified` compares the untrimmed `description.value` and `url.value` against `props.source`. As a result, typing only whitespace into an empty `description` or `url` (or adding trailing spaces to an existing value) enables the Save button even though `save()` will emit an unchanged payload.
**Suggestion:** Compare the trimmed values in `isModified` (and consider trimming `name` consistently as done in `RecipeEditor.vue`):

```ts
const isModified = computed((): boolean =>
  props.source
    ? name.value.trim() !== props.source.name ||
      description.value.trim() !== (props.source.description ?? '') ||
      url.value.trim() !== (props.source.url ?? '')
    : true,
);
```

**Why:** Keeping the modification check aligned with the normalization performed in `save()` prevents no-op saves when a user only adds or removes leading/trailing whitespace.

[CLN-002]
**Issue:** `SourceEditor.vue` trims `description` and `url` and omits them from the emitted `save` payload when blank or whitespace-only, but `src/components/sources/__tests__/SourceEditor.spec.ts` does not yet assert that whitespace-only or cleared optional fields are omitted (and surrounding whitespace is trimmed) when saving.
**Suggestion:** Add test cases in `src/components/sources/__tests__/SourceEditor.spec.ts` covering whitespace trimming and clearing existing optional fields on update:

```ts
it('trims description and url and omits them when blank or whitespace-only', async () => {
  wrapper = mountComponent();
  const nameInput = wrapper.findComponent('[data-testid="name-input"]').find('input');
  const descriptionInput = wrapper.findComponent('[data-testid="description-input"]').find('textarea');
  const urlInput = wrapper.findComponent('[data-testid="url-input"]').find('input');
  const saveButton = wrapper.findComponent('[data-testid="save-button"]');

  await nameInput.setValue('Somewhere Else');
  await descriptionInput.setValue('   ');
  await urlInput.setValue('  https://example.com/bistro  ');
  await flushPromises();
  await saveButton.trigger('click');

  expect(wrapper.emitted('save')).toEqual([[{ name: 'Somewhere Else', url: 'https://example.com/bistro' }]]);
});
```

**Why:** Directly testing the trimming and omission logic protects the contract between `SourceEditor` and the create/update pages against regressions.

[POS-001]
**Issue:** URL validation rule implementation and test coverage in `src/core/validation-rules.ts` and `src/core/__tests__/validation-rules.spec.ts`.
**Suggestion:** Using the native `URL` constructor and restricting `protocol` to `'http:'` or `'https:'` is a clean, dependency-free approach that also blocks dangerous schemes such as `javascript:` and `data:`. The accompanying unit tests thoroughly cover edge cases including IPv6 literals, ports, uppercase schemes, surrounding whitespace, and rejected schemes.
**Why:** Restricting stored URLs to `http:` and `https:` at validation time provides defense-in-depth against XSS if `source.url` is rendered in an `<a :href="source.url">` link in subsequent work.
**Documentation:** https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html

[POS-002]
**Issue:** Fixture lookup helpers in `src/components/sources/__tests__/SourceEditor.spec.ts`.
**Suggestion:** The `sourceWith` and `sourceWithout` helpers are a great pattern for selecting test fixtures by capability rather than hardcoded array indices.
**Why:** Decoupling initialization tests from specific `TEST_SOURCES` array indices makes the test suite easier to read and resilient to future fixture changes.

[QST-001]
**Issue:** When editing an existing source that already has a `description` or `url`, clearing either field in `SourceEditor.vue` causes `save()` to omit that property from the emitted `Source` object (`{ id, name }`). Because `updateSource` in `src/data/sources.ts` passes `fields` directly to Firestore's `updateDoc(docRef, fields)`, omitted properties are not removed from the Firestore document—meaning a user currently cannot clear an existing `description` or `url` once saved.
**Suggestion:** Should clearing an optional field on an existing source remove it in Firestore? If so, `updateSource` in `src/data/sources.ts` could map omitted optional fields to `deleteField()` (or `Source` could allow `null` like `Recipe.description` in `RecipeEditor.vue`):

```ts
const updateSource = async (id: string, fields: Omit<Source, 'id'>): Promise<void> => {
  await updateDoc(doc(db, `${path}/${id}`), {
    name: fields.name,
    description: fields.description ?? deleteField(),
    url: fields.url ?? deleteField(),
  });
};
```

**Why:** Firestore's `updateDoc` only modifies keys present in the payload and ignores omitted keys, so without `deleteField()` (or `null`), previously saved `description` and `url` values will remain in Firestore after a user clears them in the UI.
