# PR #484 Review — Improves recipe name uniqueness validation

## Summary

Reviewed the resulting diff for `src/components/recipes/RecipeEditor.vue` and `src/components/recipes/__tests__/RecipeEditor.spec.ts` (fixes #483). The change narrows the `recipeNames` list used by `mustBeUnique` so homemade recipes are only compared with other homemade recipes (including legacy records with no `kind`), and prepared recipes only with prepared recipes from the same source. Because `recipeNames` is a computed value that depends on `sourceId`, the existing `watch([loading, recipeNames], ...)` re-validates the name automatically whenever the source changes, so no extra wiring was needed. The new tests cover the reported bug, case and whitespace folding, the record being edited keeping its own name, and re-validation when the source changes. All 134 tests in the spec pass locally, and ESLint is clean. **Recommendation: approve.** The remaining items are small test-hygiene cleanups and one behavior question.

## Findings

### 🧹 Code cleanup and maintainability

[CLN-001]

**Issue:** The legacy-record test uses `as any` to build a recipe with `kind: undefined`. It is the only `as any` in the spec file, and it turns off type checking for the whole object literal, not just the `kind` field.

**Suggestion:** Narrow the escape hatch to the one field that intentionally breaks the type:

```typescript
{
  ...TEST_RECIPES[0]!,
  id: 'kind-undefined-1',
  name: storedName,
  kind: undefined,
} as unknown as Recipe,
```

Alternatively, spread a `Partial<Recipe>` / `Omit<Recipe, 'kind'>` and cast once to `Recipe`.

**Why:** If someone later renames a field in this fixture (for example `name`), `as any` hides the typo. `as unknown as Recipe` still states the intent ("this models legacy data that doesn't match the current type") while keeping the rest of the literal type-checked.

**Documentation:** https://www.typescriptlang.org/docs/handbook/2/everyday-types.html

[CLN-002]

**Issue:** Five of the eight new tests exercise the prepared editor, but they live inside the homemade `name` describe block. Each one calls `mountPreparedEditor`, which unmounts the homemade wrapper created by `beforeEach`, sets up sources, and mounts again. The file already has a `describe('prepared', ...)` block (around line 790) whose `beforeEach` does the same setup (`sources = TEST_SOURCES`, `mountComponent({ kind: 'prepared' })`).

**Suggestion:** Move the prepared-kind uniqueness tests into a `describe('name', ...)` (or `describe('name uniqueness', ...)`) under the existing `prepared` block. That lets them rely on the shared `beforeEach`, leaving only the homemade cases (prepared name on a homemade editor, case/space folding, legacy `kind: undefined`) where they are now. The one test that needs a specific `recipe` prop can still remount locally.

**Why:** It removes the mount → unmount → remount cycle, keeps each describe block about one editor kind, and makes it easier to find prepared-recipe behavior later.

[CLN-003]

**Issue:** The `recipeNames` filter predicate now combines three conditions inline, and the third (`props.kind === 'homemade' || x.sourceId === sourceId.value`) takes a moment to read as "the same source only matters for prepared recipes."

**Suggestion (optional):** Give the rule a name:

```typescript
const isSameNameScope = (x: Recipe) =>
  (x.kind || 'homemade') === props.kind && (props.kind === 'homemade' || x.sourceId === sourceId.value);

const recipeNames = computed((): string[] =>
  recipes.value.filter((x) => x.id !== props.recipe?.id && isSameNameScope(x)).map((x) => x.name),
);
```

**Why:** The scoping rule is the actual business rule from #483. Naming it documents the intent without a comment, and makes it easy to reuse if another screen (for example, a duplicate or import flow) needs the same check.

### ✅ Positive feedback

[POS-001]

**Issue:** None. The fix is minimal and correct.

**Suggestion:** What worked well: the change is limited to the computed list that feeds the existing `mustBeUnique` rule, so the validation rule and its case and whitespace handling are unchanged. `(x.kind || 'homemade')` uses the same fallback as the `kind` prop default, so legacy records are classified the same way in both places. Since `recipeNames` depends on `sourceId`, the existing watcher re-validates when the source changes, with no new watchers or event handlers.

**Why:** It fixes the bug with very little new surface area, and it reuses the reactivity that is already in place instead of adding a parallel path.

**Issue:** None.

**Suggestion:** What worked well: the tests cover each side of the new rule (accept across kinds, accept across sources, reject within the same scope), along with the edge cases: trim and case folding, legacy `kind: undefined`, the record being edited keeping its own name, and switching sources back and forth. ### 💭 Questions for discussion

[QST-001]

**Issue:** On a new prepared recipe with no source selected yet, `sourceId.value` is `null`. No stored prepared recipe will match that, so the name never shows "already exists" until a source is chosen. The `rechecks the name when the selected source changes` test confirms the error then appears, and save is blocked without a source anyway, so this is not a correctness hole.

**Suggestion:** Confirm this is the intended UX. If it is, consider a short test that locks it in, for example "does not flag a duplicate name before a source is selected." If not, one option is to compare against all prepared recipes while no source is selected.

**Why:** Pinning the behavior down either way keeps a later refactor from changing it by accident.
