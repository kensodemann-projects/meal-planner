**Suggestion:** Remove `PLAN.md` from the branch before merging (and optionally add `/PLAN.md` to `.gitignore` so local planning artifacts are not staged accidentally):

**[CLN-002]**

**Issue:** In `src/pages/dashboard/recipes.vue` (line 48), `isMealQuery` uses the `in` operator (`value in MEAL_QUERIES`), which walks `Object.prototype`. Query values such as `?mealType=toString` or `?mealType=constructor` evaluate to `true` in `isMealQuery`, causing `loadMealRecipes` and `getMealPlanForDate` to run for an unrecognized meal type while `heading` evaluates to `undefined`.  
**Suggestion:** Use `Object.hasOwn` so only own keys of `MEAL_QUERIES` narrow to `MealQuery`:

```typescript
const isMealQuery = (value: unknown): value is MealQuery =>
  typeof value === 'string' && Object.hasOwn(MEAL_QUERIES, value);
```

**Why:** `Object.hasOwn` checks only own properties on `MEAL_QUERIES`, preventing inherited `Object.prototype` property names from bypassing the unrecognized-query guard.  
**Documentation:** https://www.typescriptlang.org/docs/handbook/2/narrowing.html

**[CLN-003]**

**Issue:** `src/pages/dashboard/recipes.vue` implements reactive `route.query.mealType` watching and stale-response cancellation via `requestGeneration` (lines 58, 66, 76, 81, 100, 105–117), but `src/pages/dashboard/__tests__/recipes.spec.ts` mocks `useRoute` as a static object and only tests the initial mount.  
**Suggestion:** Back the mocked `route.query` with a `reactive` object in `src/pages/dashboard/__tests__/recipes.spec.ts` and add a test verifying that changing `route.query.mealType` while an earlier lookup is pending discards the stale result and renders the newer meal:

```typescript
import { reactive } from 'vue';

const routeState = reactive<{ query: Record<string, unknown> }>({
  query: { mealType: 'breakfast' },
});
(useRoute as Mock).mockReturnValue(routeState);
```

**Why:** Directly testing query transitions and out-of-order promise resolution protects the `requestGeneration` guard against future regressions.

**[POS-001]**

**Issue:** Type-safe query mapping and resilient concurrent recipe loading in `src/pages/dashboard/recipes.vue`.  
**Suggestion:** Using `as const satisfies Record<string, { heading: string; mealType: MealType }>` for `MEAL_QUERIES` along with per-item `try/catch` inside `Promise.all` (lines 34–39, 90–98) is a great pattern.  
**Why:** It gives compile-time verification of the query-to-model mapping and guarantees that a single deleted or failing recipe does not abort sibling lookups or disturb `meal.items` ordering.  
**Documentation:** https://www.typescriptlang.org/docs/handbook/2/everyday-types.html

**[POS-002]**

**Issue:** Comprehensive behavioral test suite in `src/pages/dashboard/__tests__/recipes.spec.ts`.  
**Suggestion:** Mounting the real `RecipeView` component with Vuetify and testing homemade vs. prepared recipes, `item.servings` vs. `recipe.servings`, pending states, and mixed resolved/unavailable item ordering provides strong confidence in the page contract without brittle implementation-detail assertions.  
**Why:** Co-located behavioral tests make the page contract clear and resilient to internal refactoring.

**[QST-001]**

**Issue:** In `src/pages/dashboard/recipes.vue` (lines 13–16), an unavailable recipe renders `{{ row.item.name }}` as a bare text node inside the row `<div>`, whereas resolved recipes render their name inside an `<h2>` via `RecipeView :heading-level="2"`. Additionally, `<h1>` and `<CloseButton>` have no layout/spacing classes (unlike `<h1 class="text-center">` in `src/pages/dashboard/index.vue` or `<div class="page-actions mt-4">` in `ViewPageActionButtons.vue`).  
**Suggestion:** Consider wrapping the unavailable item name in `<h2>{{ row.item.name }}</h2>` so every meal item shares the same heading level in the document outline, and confirm whether page spacing/heading alignment is intentionally deferred:

```vue
<template v-else>
  <h2>{{ row.item.name }}</h2>
  <p>Recipe unavailable.</p>
</template>
```

**Why:** Giving unavailable items an `<h2>` keeps the heading hierarchy consistent across all planned items on the page and avoids adjacent unwrapped text nodes.  
**Documentation:** https://www.w3.org/WAI/ARIA/apg/
